Fix `AsyncApiDocumentService` silently dropping payload data whenever two different types (or two different operations/messages) produced the same sanitized component key. Schema and message component keys were derived independently from the bare CLR type name (`payloadType.Name`), completely ignoring a configured `AsyncApiOptions.CreateSchemaReferenceId`, and whenever the computed key already existed in `components.schemas`/`components.messages` the existing entry was silently kept — so two payload classes with the same short name in different namespaces (e.g. `Order.V1.Created` and `Order.V2.Created`), two different closed generic types over the same open generic definition (e.g. `Envelope<Foo>` and `Envelope<Bar>`, whose CLR `Type.Name` is identical regardless of the type argument), or two different operations/messages that happened to sanitize to the same id, would generate successfully but with one of the two payloads' schema/properties missing from the document entirely, with no warning.

Schema and message component keys are now derived through the same authoritative path the schema generator already uses to resolve `CreateSchemaReferenceId` for a type, so a custom reference id is honored consistently everywhere a component key is built, and returning `null` from it reliably inlines the schema (per its documented contract) instead of still being added to `components/schemas` under a default key. When two genuinely different payload types, messages, or operations would still collide on the same key after sanitization, generation now throws a clear `InvalidOperationException` naming both conflicting types/members instead of silently discarding one of them — the same payload `Type` reused across multiple channels continues to be deduplicated into a single shared component, which is unaffected by this change.
